# Речь — модуль интерфейса (~5 минут)

> Заголовки в скобках — только для ориентира, вслух не читать.
> Каждая строка — отдельная мысль. Читай плавно, без пауз между строками.

---

[[ ЧТО УМЕЕТ ИНТЕРФЕЙС ]]

Платформа обслуживает три категории пользователей: студент, преподаватель и администратор.
У каждого свой личный кабинет и свои права доступа.

Интерфейс построен как одностраничное приложение — при первом заходе один раз скачивается код, и после этого все переходы происходят мгновенно, без перезагрузки страницы.
Для платформы, где пользователь постоянно переключается между уроками и заданиями, это принципиально важно.

---

[[ ТЕХНОЛОГИИ ]]

Основа интерфейса — React: интерфейс собирается из готовых компонентов, каждый написан один раз и используется в любом месте приложения.

Код написан на TypeScript — он проверяет типы данных ещё до запуска приложения, как проверка орфографии в Word: выявляет проблемы до того, как они доходят до пользователя.

За сборку отвечает Vite: удаляет неиспользуемый код, сжимает файлы и загружает только нужное.
Стилизация — TailwindCSS: готовые классы прямо в разметке, без отдельных CSS-файлов. Адаптивность под любой экран задаётся там же — через префиксы sm, md, lg.
Навигация — React Router: управляет переходами между страницами внутри браузера, без перезагрузки. Он же отвечает за защиту маршрутов по ролям — студент не попадёт на страницу администратора даже по прямой ссылке.
Из дополнительных инструментов: Framer Motion для плавных анимаций переходов, Lucide для иконок, Prism для подсветки синтаксиса кода в уроках.
Для визуальных эффектов на лендинге реализованы два собственных компонента: интерактивный глобус из бинарных цифр, где точки на карте мира изображают «активных студентов», и анимированная сеть частиц — фон hero-секции, где точки соединяются линиями и реагируют на движение мыши. Оба компонента написаны на Canvas 2D API браузера — без сторонних графических библиотек. Это даёт полный контроль над анимацией и не увеличивает вес страницы.

Всего в проекте 22 экрана: кабинеты всех трёх ролей, прохождение курса, аналитика, настройки и служебные экраны.

---

[[ БЕЗОПАСНОСТЬ ]]

Все закрытые страницы защищены компонентом-охранником — он проверяет, вошёл ли пользователь и достаточно ли у него прав.
Страница администратора недоступна студенту даже по прямой ссылке.

После входа система выдаёт два токена: краткосрочный на 60 минут и долгосрочный на 7 дней.
Когда первый истекает — второй тихо выдаёт новый. Пользователь не замечает этого и не выходит из системы принудительно.

---

[[ СТРУКТУРА КОДА ]]

Код разделён на четыре слоя.
Страницы — это то, что видит пользователь: 22 экрана для всех трёх ролей.
Компоненты — переиспользуемые кирпичики: кнопки, карточки, модальные окна — написаны один раз и работают везде.
Модули логики — авторизация, запросы к серверу, работа с формами — отделены от визуальной части.
Сервисы — связь с API: все запросы к бэкенду идут через единый слой, и при смене URL достаточно поменять одну строку.

Такое разделение упрощает доработку: чтобы добавить новый экран, не нужно трогать логику, а чтобы поменять логику — не нужно трогать вёрстку.

## Вероятные вопросы и короткие ответы

**«Почему не взяли готовую платформу, например Moodle?»**
Готовые платформы плохо поддаются кастомизации — под задачу с тремя ролями, AI-обратной связью и специфической аналитикой проще строить с нуля, чем ломать чужую архитектуру.

**«Чем ваш интерфейс отличается от, например, Coursera?»**
Интеграция AI-обратной связи прямо в поток прохождения урока, не как отдельный инструмент. И закрытая экосистема, где преподаватель сам создаёт и публикует курсы без модерации.

**«Проводилось ли автоматическое тестирование?»**
Автоматические тесты — следующий шаг развития. На текущем этапе объём сценариев позволял покрыть всё ручным тестированием.

**«Как приложение ведёт себя при медленном интернете?»**
Благодаря разбиению на части каждый раздел подгружается отдельно. Пользователь видит загрузку только для нужного раздела, остальной интерфейс остаётся рабочим.

**«Почему React, а не Vue или Angular?»**
React — самый распространённый выбор в индустрии, под него больше готовых решений и документации. Vue ближе к нему по простоте, но экосистема меньше. Angular избыточен для проекта такого масштаба — он рассчитан на большие корпоративные команды с жёсткими стандартами.

**«Как хранится состояние приложения — используется ли Redux?»**
Redux не использовался — он оправдан при очень сложном общем состоянии. Здесь достаточно встроенного Context API в React: данные о пользователе и авторизации хранятся в контексте и доступны из любого компонента без лишней сложности.

**«Как фронтенд общается с бэкендом, если токен истёк прямо во время работы?»**
Это обрабатывается автоматически. Когда сервер возвращает ошибку 401, фронтенд перехватывает её, незаметно запрашивает новый токен через долгосрочный refresh-токен и повторяет исходный запрос. Пользователь ничего не замечает.

**«Как реализована защита маршрутов?»**
Каждый защищённый маршрут обёрнут в компонент-охранник. При попытке зайти на закрытую страницу без авторизации — редирект на страницу входа. При попытке зайти на страницу с недостаточными правами — редирект на главную. Это работает и при прямом вводе URL в адресную строку.

**«Адаптирован ли интерфейс под мобильные устройства?»**
Да, вёрстка адаптивная — TailwindCSS позволяет задавать стили для разных размеров экрана прямо в разметке. Основные экраны проверены на ширинах от 375px (мобильный) до 1440px (десктоп).

**«Как отображается код в уроках, есть ли подсветка синтаксиса?»**
Да, используется библиотека Prism. Она подсвечивает синтаксис для большинства популярных языков — Python, JavaScript, SQL и других — прямо в браузере, без серверной обработки.

**«Как реализована защита маршрутов на уровне интерфейса?»**
Каждый закрытый маршрут обёрнут в компонент-охранник. До отрисовки страницы он проверяет наличие токена и роль пользователя. Если токена нет — редирект на страницу входа. Если роль не та — редирект на главную. Это работает и при прямом вводе URL в адресную строку.

**«Как организовано взаимодействие с API — каждый компонент сам делает запросы?»**
Нет, все запросы к серверу вынесены в отдельный сервисный слой. Компонент вызывает функцию из сервиса и получает готовые данные. Это значит, что если поменяется адрес API или формат ответа — правки нужны только в одном месте, а не по всему проекту.

**«Как обрабатываются ошибки сети или сервера на фронтенде?»**
Все запросы проходят через единый перехватчик. Если сервер вернул 401 — автоматически запрашивается новый токен и запрос повторяется. Если сервер вернул другую ошибку — пользователь видит понятное сообщение, а не пустой экран или зависший интерфейс.

**«Как реализована адаптивная вёрстка?»**
TailwindCSS позволяет задавать стили для разных размеров экрана прямо в разметке через префиксы: sm, md, lg. Отдельных CSS-файлов для мобильной версии нет — всё в одном месте. Интерфейс проверен на ширинах от 375px до 1440px.

**«Как реализована смена темы, сохраняется ли выбор?»**
Выбор темы сохраняется в localStorage — хранилище браузера, которое не очищается при закрытии вкладки. При загрузке приложения тема считывается и применяется до отрисовки интерфейса, чтобы не было мерцания. Тёмная тема реализована через CSS-переменные и переключение класса на корневом элементе страницы.

**«Как управляется общее состояние приложения — Redux?»**
Redux не использовался, он избыточен для данного масштаба. Глобальные данные — авторизация, профиль пользователя, тема — хранятся в Context API, это встроенный механизм React. Локальное состояние каждого экрана управляется внутри самого компонента.

**«Как устроена сборка проекта для продакшена?»**
Сборку выполняет Vite. Он анализирует весь код, удаляет неиспользуемые части, разбивает результат на небольшие файлы и сжимает их. Итог — папка с готовыми статическими файлами, которые отдаёт веб-сервер. Браузер загружает только тот код, который нужен для конкретной страницы.
